Kontynuujemy wdrażanie ręcznej enklawy Orcan Studio (etapy 0–2 roadmapy).
Użytkownik zatwierdził rozpoczęcie implementacji. Automatyzacja pozostaje planem.

Przeczytaj kolejno:
1. AGENTS.md i .manifest.json workspace’u.
2. .orcan/session-brief.md — aktualny handoff.
3. Instrukcje projektu Orcan.
4. docs/en/ideas/orcan-studio-roadmap.md — trwały plan.
5. docs/en/ideas/orcan-studio.md — opis obecnej implementacji.

Dokumentacja kierunku nie jest dowodem wdrożenia. Porównuj ją z kodem i testami.

Pierwszy etap: RĘCZNIE UŻYTECZNA ENKLAWA, bez automatyzacji.

Kolejność użytkownika:
- Opcjonalnie utwórz tożsamość w Studio.
- Połącz się z serwerem/VM i wykonaj provisioning CLI/obrazu.
- W Servers utwórz i uruchom kontener z tożsamością lub Default.
- Dobierz istniejące kontenery z jednej lub wielu VM do enklawy.
- Ułóż karty na planszy 2D i zapisz grupę.
- Attach do konkretnego kontenera/workspace’u; ręcznie zaloguj się do agenta.

Ustalenia:
- Biblioteka tożsamości jest sekcją jak Profile/Credentials: nazwa, opis,
  textarea Markdown. identity.json + instructions.md, wersjonowanie szablonów.
  Tożsamość opisuje też efektywnego developera i nastawienie na cel, nie tylko
  rolę review. Ogólne AGENTS.md/CLAUDE.md Orcana pozostają bazą. Markdown dodaje
  instrukcje; JSON jest wyłącznie metadanymi, bez liczbowych priorytetów.
- Tożsamość przesyłamy i adaptujemy tylko przy tworzeniu kontenera. Jego kopia
  i wersja są niezmienne. Inna tożsamość wymaga jawnego usunięcia i utworzenia
  kontenera zastępczego, z zachowaniem danych projektów. Default to bazowe
  instrukcje Orcana bez dodatkowej roli; istniejące kontenery pozostają Default.
- VM może proponować domyślną tożsamość nowych kontenerów. Orcan propaguje
  przypisaną kopię przez obecne workspace context packs (AGENTS.md/CLAUDE.md)
  do wszystkich istniejących i nowych workspace’ów. Zachowaj reguły własne
  i instrukcje repozytoriów. Tożsamość nie zawiera sekretów ani uprawnień.
- Enklawa dobiera kontenery, nie VM/workspace’y. Kontener może być w kilku
  enklawach. Linie, zapis układu i otwarcie grupy niczego nie uruchamiają.
- Karta ma Attach. Zatrzymany kontener wymaga jawnego Start i weryfikacji;
  brak/offline nie powoduje cichego odtworzenia. Zamknięcie terminala nie
  usuwa kontenera ani nie kończy automatycznie trwałej sesji tmux.
- UUID służą do referencji; nazwy do wyświetlania, profile do transportu.
  Sprawdzaj cel po uwierzytelnieniu SSH. Restart/zmiana nazwy zachowują ID,
  nowy kontener i klon VM potrzebują nowych ID. Probe pozostaje read-only.
- Nowe dane identities/enclaves/runs są w studio-data/ obok zainstalowanej
  aplikacji, niezależnie od katalogu uruchomienia. JSON/Markdown, przycisk
  „Otwórz katalog danych”, kopiowanie i ręczne sprzątanie po zamknięciu Studio.
  Aktualizacja zachowuje dane; brak zapisu ma jawny błąd bez cichego fallbacku.
  Usunięcie lokalnych danych nie usuwa danych na VM ani nie ponawia pracy.
  Nie przenoś istniejących profili ani sekretów w ramach tego planu.

Najpierw domknij projekt: skład instrukcji, Attach na każdej platformie,
UUID/klonowanie, konfigurację zastępczego kontenera, lokalizację danych oraz
minimalny wygląd planszy i stany offline/stale. Pierwszy blok wyrównał helper Git
i rejestr probe ze ścieżkami instancji; nowe kontenery dostają namespace z Compose.
Kolejny blok wdrożył bibliotekę tożsamości i wybór wersji przy tworzeniu kontenera,
zamrożenie kopii w konfiguracji oraz propagację do AGENTS.md/CLAUDE.md workspace’ów.
Dane wersji są w studio-data/identities/<UUID>/versions/<version>/ obok aplikacji.
Tożsamość wymaga nowego CLI i obrazu; istniejący runtime nie został przebudowany.
Kolejny blok wdrożył UUID hostów/kontenerów, jawną archiwizację konfiguracji
zastępowanego kontenera oraz zapis enklaw na planszy Vue Flow. Karty mają Check,
Start i Attach; połączenia są wyłącznie wizualne. UUID oznacza logiczny cel:
Down/ponowne uruchomienie z tą samą konfiguracją zachowuje ID, jawne zastąpienie
nadaje nowe. Klon VM wymaga jawnego target clone/register --new-target;
skopiowanego machine-id nie da się automatycznie odróżnić. Probe nie zapisuje ID.
Attach obsługuje lokalny terminal, WSL i system SSH; SSH wymaga agenta systemowego,
nie przekazuje zapisanych haseł/kluczy do terminala. Rzeczywiste Windows/WSL/SSH
i instalatory pozostają do sprawdzenia na testowych maszynach, bez restartu
runtime’u użytkownika. Dalszy etap to takie sprawdzenie, nie automatyzacja.

DALSZA OPCJA, nie wymóg pierwszego etapu:
- GitHub PR / GitLab MR na przypiętych base/head: Tester → Reviewer → człowiek.
  Enklawa może też zbierać niezależne perspektywy na tę samą rewizję obok siebie;
  sekwencyjny przepływ nie jest wymagany. Początkowo oceny zlecamy ręcznie.
- Studio steruje, Orcan wykonuje, agent oddaje report.md + result.json.
- Reuse inbox/executor, bez wymogu MCP. Tryb agenta zależy od zweryfikowanego
  interfejsu; dedykowany workspace i osobny proces nie są obowiązkowe.
- Jedno zadanie automatyczne na workspace między enklawami; uwzględnij
  wspólne zapisywalne katalogi. Attempt ID blokuje podwójne wykonanie.
- Studio musi działać, aby uruchamiać kolejne kroki. Reconnect odzyskuje stan.
- Retencja wyników/logów/artefaktów: 7 dni; krótka historia: 30 dni, od końca
  całego przebiegu. Chroń aktywne, oczekujące na review, zależne i „Zachowaj”.
- Sześć decyzji przed automatyzacją opisano w roadmapie. Bez pętli poprawek,
  automatycznego merge/push; publikacja komentarzy/review jest jawna.

Preferuj minimalizm i wykorzystanie istniejących mechanizmów. Nie cofaj zmian,
nie przebudowuj ani nie restartuj kontenera użytkownika. Testy jednostkowe nie
zastępują rzeczywistego sprawdzenia Windows → WSL2 → SSH na testowych VM.
